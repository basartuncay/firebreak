# Contributing to Firebreak

Firebreak is maintained by one person. Small, focused changes are the easiest to review.

## Set up

Node.js 20 or newer.

```bash
git clone https://github.com/basartuncay/firebreak && cd firebreak
npm ci
```

## Check your change

CI (`.github/workflows/ci.yml`) runs these four, in this order. Run them before you open a pull request:

```bash
npm run lint        # biome: lint and formatting, Markdown included
npm run typecheck
npm run build
npm test            # vitest
```

`npm run format` fixes what `npm run lint` reports about formatting.

## Run the scenario corpus

`firebreak test` replays every scenario in `scenarios/` against a policy, with no model involved:

```bash
npm run build
node dist/cli.js test                      # built-in corpus, default policy
node dist/cli.js test --format markdown    # the report the GitHub Action prints
node dist/cli.js test --no-builtin --scenarios ./my-scenarios --policy ./policy.yaml
```

- A scenario is one YAML file: the tool results the agent read, then the call the attacker wants, then
  `expect: blocked` or `expect: allowed`. `scenarios/firebreak/attacks/base64-address.yaml` is a short one
  to copy from.
- `scenarios/cordon/` is generated by `scripts/import-cordon.py`. Change the script, not the files.
- `knownMiss: true` marks a scenario that is expected to fail today; its `notes` say why. These are the
  misses listed in [docs/results.md](docs/results.md).
- The headline numbers are pinned by a snapshot in `tests/testsuite.test.ts`. If your change moves them,
  update `docs/results.md` and the "Results" section of the README in the same pull request and say why
  they moved.

To look at the dashboard with demo data:

```bash
FIREBREAK_HOME=/tmp/fb npx tsx scripts/seed-demo.ts && FIREBREAK_HOME=/tmp/fb node dist/cli.js ui
```

## Rules for a change

- This is a security tool. A change that lets a previously held scenario through is a regression, even if
  the tests are updated to match. Say so explicitly in the pull request.
- Do not update snapshots blindly. Explain each snapshot diff.
- Fail closed: on errors or unknown input, hold the call rather than allow it.
- Update `CHANGELOG.md` for user-visible changes.

## A good first change

- **A new scenario** under `scenarios/firebreak/`. The corpus has only 10 benign tasks, which is too few
  to measure friction, so realistic benign tasks are especially useful. Write the `expect` you believe is
  right; if Firebreak gets it wrong today, mark it `knownMiss: true` with a note.
- **One of the documented limits.** The README's "Limits" section and the "ten attacks that get through"
  in `docs/results.md` describe what Firebreak misses and why. Three scoped starting points are written
  up in [docs/issue-drafts/](docs/issue-drafts/).
- **Documentation** that is wrong or unclear, with the command or file that shows it.

Where things live: `src/provenance/` (what is remembered from tool results), `src/policy/` and
`src/classify.ts` (allow, hold or block), `src/proxy.ts` and `src/jsonrpc.ts` (MCP proxying),
`src/store/`, `src/ui/` and `web/` (approval queue and dashboard), `src/testsuite/` and `scenarios/` (the
attack suite). Design: [docs/design.md](docs/design.md) and [docs/threat-model.md](docs/threat-model.md).

## Security bugs

Do not open a public issue for a bypass. Report it privately as described in [SECURITY.md](SECURITY.md).
The documented limits are not vulnerabilities; ideas for closing them are welcome as regular issues.
